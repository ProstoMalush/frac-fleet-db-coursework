# План индексации и проверки производительности

## Три целевых индекса

### 1. B-tree: `idx_repair_stage_started_at_btree`

Таблица: `frac_core.repair_stage`, столбец `started_at`.

Назначение: поиск этапов ремонта за временной диапазон. B-tree подходит для сравнений по диапазонам дат и упорядоченного чтения.

### 2. Составной частичный B-tree: `idx_well_repair_active_fleet_start`

Таблица: `frac_core.well_repair`, столбцы `(frac_fleet_id, planned_start_at DESC)` с предикатом `repair_status IN ('planned', 'in_progress')`.

Назначение: быстро находить запланированные и выполняемые ремонты выбранного флота за период. Завершённые и отменённые операции не занимают место в частичном индексе.

### 3. BRIN: `idx_telemetry_measured_at_brin`

Таблица: `frac_core.telemetry_measurement`, столбец `measured_at`.

Назначение: диапазонное чтение временного ряда. BRIN хранит сводки по диапазонам страниц и эффективен, когда физический порядок строк коррелирует со временем измерения. Для этого в учебном эксперименте используется `CLUSTER`.

## Воспроизведение эксперимента

Полный сценарий расположен в `performance/`:

1. `00_table_sizes.sql` — размеры таблиц и индексов.
2. `00b_cluster_telemetry_by_time.sql` — физически упорядочить телеметрию по `measured_at`; выполнить до baseline, если требуется повторить демонстрацию BRIN.
3. `01_prepare_baseline.sql` — временно удалить три исследуемых индекса и обновить статистику.
4. `02_explain_before.sql` — выполнить три запроса `EXPLAIN (ANALYZE, BUFFERS, VERBOSE)` без целевых индексов.
5. `03_create_target_indexes.sql` — создать три индекса обратно.
6. `04_explain_after.sql` — выполнить те же запросы после индексации.
7. `05_index_catalog.sql` и `06_index_usage_stats.sql` — проверить определения и использование индексов.

После шага 3 обязательно выполнить шаг 5: целевые индексы должны быть восстановлены.

## Результаты контрольного запуска пользователя

| Запрос | План до | Время до, мс | План после | Время после, мс |
|---|---|---:|---|---:|
| Поиск этапов по `started_at` | Seq Scan + Sort | 0,230 | Index Scan | 0,057 |
| Активные ремонты по флоту и дате | Seq Scan + Sort | 0,083 | Index Scan | 0,055 |
| Телеметрия за период | Seq Scan + Sort | 3,952 | Bitmap Index Scan (BRIN) + Bitmap Heap Scan | 0,728 |

Это фактические времена конкретного учебного запуска. Измерения зависят от аппаратуры, кэша, статистики и состояния PostgreSQL и не являются гарантией для других окружений.

## Почему потребовался CLUSTER

До физической сортировки корреляция `pg_stats.correlation` для `measured_at` составляла примерно `0,0362`; планировщик выбирал `Seq Scan`. После `CLUSTER` значение составило `1,0`, и BRIN стал использоваться в плане. В одном контрольном запуске для телеметрии число shared buffers сократилось с 566 до 66.

Для небольших таблиц или широких временных диапазонов PostgreSQL может предпочесть `Seq Scan`. Это нормальное решение оптимизатора, а не ошибка индекса.
