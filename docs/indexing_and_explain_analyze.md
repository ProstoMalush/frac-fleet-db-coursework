# Этап 7. Индексы и EXPLAIN ANALYZE

## Цель

Оценить три индекса PostgreSQL 15 на реальных запросах проекта:

1. B-tree `idx_repair_stage_started_at_btree` по `frac_core.repair_stage.started_at`.
2. Составной частичный B-tree `idx_well_repair_active_fleet_start` по `(frac_fleet_id, planned_start_at DESC)` для статусов `planned` и `in_progress`.
3. BRIN `idx_telemetry_measured_at_brin` по `frac_core.telemetry_measurement.measured_at`.

## Порядок воспроизведения

1. `00_table_sizes.sql` — сохранить размеры таблиц.
2. `00b_cluster_telemetry_by_time.sql` — физически упорядочить телеметрию по времени для демонстрации BRIN.
3. `01_prepare_baseline.sql` — временно удалить целевые индексы (и старое имя индекса по дате ремонта, если оно осталось) и обновить статистику.
4. `02_explain_before.sql` — выполнить три `EXPLAIN (ANALYZE, BUFFERS, VERBOSE)` отдельно.
5. `03_create_target_indexes.sql` — создать/восстановить три целевых индекса.
6. `04_explain_after.sql` — повторить те же запросы.
7. `05_index_catalog.sql` — проверить определения индексов.
8. `06_index_usage_stats.sql` — посмотреть статистику использования.

**Важно:** после baseline обязательно выполнить шаг 5, чтобы восстановить целевые индексы. Шаг 2 использует `CLUSTER`, который переписывает физический порядок строк таблицы и требует блокировки таблицы на время операции; логические значения строк не меняются.

## Результат контрольного запуска пользователя

| Запрос | План до | Время до, мс | План после | Время после, мс |
|---|---|---:|---|---:|
| Поиск этапов по `started_at` | Seq Scan + Sort | 0,230 | Index Scan | 0,057 |
| Активные ремонты по флоту и дате | Seq Scan + Sort | 0,083 | Index Scan | 0,055 |
| Телеметрия за диапазон дат | Seq Scan + Sort | 3,952 | Bitmap Index Scan (BRIN) + Bitmap Heap Scan | 0,728 |

Измеренное ускорение в этом запуске: около 4,04 раза, 1,51 раза и 5,43 раза соответственно. Это результаты конкретного учебного окружения; они зависят от аппаратуры, прогрева кэша, статистики и состояния PostgreSQL и не являются гарантией для других сред.

## Почему потребовался CLUSTER

До физической сортировки `pg_stats.correlation` для `measured_at` составляла примерно `0,0362`; планировщик выбирал `Seq Scan`. После `CLUSTER` значение стало `1,0`, и BRIN стал использоваться в плане через `Bitmap Index Scan` / `Bitmap Heap Scan`.

В одном из запусков после индексации для телеметрии было `Buffers: shared hit=66`, тогда как baseline показывал `shared hit=566`. При сравнении также учитывайте `Rows Removed by Index Recheck` для lossy BRIN-страниц.

## Интерпретация

Индекс не обязан выбираться планировщиком во всех условиях. Для небольших таблиц или широких диапазонов `Seq Scan` может быть дешевле. В отчёте приводятся фактические планы, а не предполагаемый выбор индекса.
