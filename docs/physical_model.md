# Физическая модель базы данных (ФМД)

## 1. Назначение

Физическая модель фиксирует реализацию логической модели в PostgreSQL 15: типы данных, схему размещения, первичные и внешние ключи, ограничения, индексы и комментарии. Операционная часть размещается в схеме `frac_core`.

Модель сохраняет 12 основных сущностей. Вспомогательные объекты PostgreSQL (расширение `btree_gist`, ограничения-исключения и индексы) не являются дополнительными сущностями предметной области.

## 2. Общие физические решения

- Идентификаторы: `BIGINT GENERATED ALWAYS AS IDENTITY`.
- Даты и время производственных событий: `TIMESTAMPTZ`, чтобы хранить однозначные моменты времени.
- Календарные даты без времени: `DATE`.
- Измеряемые величины: `NUMERIC` с явно заданной точностью, а не `FLOAT`, чтобы избежать двоичных ошибок округления в отчётных значениях.
- Коды и короткие наименования: `VARCHAR` ограниченной длины; описания: `TEXT`.
- Для большинства внешних ключей: `ON UPDATE CASCADE ON DELETE RESTRICT`.
- Имена таблиц и столбцов — в `snake_case`, нижний регистр.
- Справочные значения статусов и категорий ограничиваются `CHECK`.

## 3. Реализация таблиц

| Таблица | Первичный ключ | Внешние ключи | Важные ограничения |
|---|---|---|---|
| `oil_field` | `oil_field_id BIGINT IDENTITY` | — | `field_code` UNIQUE; коды и названия NOT NULL |
| `well` | `well_id BIGINT IDENTITY` | `oil_field_id → oil_field` | UNIQUE (`oil_field_id`, `well_code`); CHECK типа, статуса и глубины |
| `frac_fleet` | `frac_fleet_id BIGINT IDENTITY` | — | `fleet_code` UNIQUE; CHECK статуса и предельного давления |
| `equipment_type` | `equipment_type_id BIGINT IDENTITY` | — | `type_code` UNIQUE; CHECK категории |
| `equipment_unit` | `equipment_unit_id BIGINT IDENTITY` | `equipment_type_id → equipment_type` | `equipment_code` UNIQUE; `serial_number` UNIQUE; CHECK года и состояния |
| `fleet_unit_assignment` | `assignment_id BIGINT IDENTITY` | `frac_fleet_id → frac_fleet`; `equipment_unit_id → equipment_unit` | CHECK дат; EXCLUDE по оборудованию и пересечению интервалов |
| `crew` | `crew_id BIGINT IDENTITY` | — | `crew_code` UNIQUE; CHECK статуса |

| `repair_stage` | `repair_stage_id BIGINT IDENTITY` | `repair_id → well_repair` | UNIQUE (`repair_id`, `stage_number`); CHECK номера, статуса и дат |
| `telemetry_measurement` | `measurement_id BIGINT IDENTITY` | `repair_stage_id → repair_stage` | UNIQUE (`repair_stage_id`, `measured_at`); CHECK неотрицательных значений и наличия хотя бы одного показателя |
| `equipment_maintenance` | `maintenance_id BIGINT IDENTITY` | `equipment_unit_id → equipment_unit` | CHECK типа, статуса и дат; запрет пересекающихся интервалов обслуживания одной единицы |

Полные описания каждого атрибута сохранены в `docs/logical_model.md`. SQL-скрипты являются точной реализацией этой модели.

## 4. Ограничения целостности

### 4.1. Первичные и внешние ключи

Каждая таблица имеет суррогатный первичный ключ. Внешние ключи обеспечивают существование родительской записи. Использование `ON DELETE RESTRICT` не позволяет удалить месторождение, скважину, флот, оборудование или иной объект, если на него ссылаются производственные записи. Для удаления тестового набора следует использовать отдельную административную процедуру, а не каскадное удаление.

### 4.2. Уникальность

Используются уникальные ограничения на бизнес-коды. Код скважины уникален внутри месторождения, так как одинаковые номера скважин могут встречаться в разных месторождениях. Временная метка телеметрии уникальна в пределах одного этапа.

### 4.3. Временные интервалы

Интервалы закрепления оборудования задаются как полуоткрытые `[assigned_at, released_at)`. Если `released_at IS NULL`, интервал считается открытым и продолжается до бесконечности. Благодаря такому представлению соседние назначения могут соприкасаться границами, но не пересекаться.

Для запрета пересечения интервалов одной единицы оборудования используется `EXCLUDE USING gist` по `equipment_unit_id` и диапазону `tstzrange`. Для равенства BIGINT в GiST требуется расширение `btree_gist`.

Для записей обслуживания аналогично запрещены пересекающиеся периоды обслуживания одной единицы оборудования. Это предотвращает двойную регистрацию параллельных работ обслуживания.

### 4.4. Производственные статусы

- Завершённый ремонт обязан иметь фактические начало и окончание.
- Завершённый этап обязан иметь начало и окончание.
- Завершённое техническое обслуживание обязано иметь дату окончания.
- Дата окончания не может предшествовать дате начала.
- Отрицательные значения давления, расхода, концентрации и накопительных объёмов запрещены.

### 4.5. Граница межтабличных правил

Обычный `CHECK` проверяет значения текущей строки и не предназначен для проверки других таблиц. Поэтому правила вида «оборудование не может использоваться в операции во время обслуживания» требуют отдельной бизнес-логики/триггера или проверки при регистрации производственной операции. В текущей версии принадлежность оборудования к флоту и его техническая доступность разделены: нахождение в составе флота не означает, что оборудование доступно к эксплуатации.

## 5. Индексы

В дополнение к индексам, автоматически создаваемым для PK и UNIQUE, используются три целевых индекса разных типов, которые исследуются в `performance/`.

| Индекс | Тип | Выражение | Назначение |
|---|---|---|---|
| `idx_repair_stage_started_at_btree` | B-tree | `repair_stage(started_at)` | Поиск этапов ремонта за диапазон времени |
| `idx_well_repair_active_fleet_start` | Составной частичный B-tree | `(frac_fleet_id, planned_start_at DESC) WHERE repair_status IN ('planned','in_progress')` | Получение запланированных и выполняемых ремонтов выбранного флота за период; завершённые и отменённые записи не включаются в индекс |
| `idx_telemetry_measured_at_brin` | BRIN | `telemetry_measurement(measured_at)` | Диапазонный поиск по времени в крупной таблице временных рядов при корреляции физического порядка строк с `measured_at` |

Дополнительно создаются поддерживающие B-tree индексы на часто используемых FK-столбцах для ускорения JOIN и проверок ссылочной целостности. Они не заменяют три целевых индекса из таблицы выше.

BRIN хранит сводную информацию по диапазонам страниц, а не отдельную запись на каждую строку. Поэтому его размер обычно меньше B-tree, но эффективность зависит от физического порядка данных. В контрольном эксперименте после `CLUSTER` корреляция `measured_at` составила `1,0`, и планировщик выбрал BRIN через `Bitmap Index Scan` и `Bitmap Heap Scan`. Для небольших таблиц или широких диапазонов PostgreSQL вправе выбрать `Seq Scan` — это нормальное решение планировщика.

Фактические планы и времена до/после приведены в [`indexing_and_explain_analyze.md`](indexing_and_explain_analyze.md).

## 6. Порядок применения SQL

1. `01_create_schema.sql` — создать схему `frac_core`.
2. `02_extensions.sql` — подключить `btree_gist`.
3. `03_create_tables.sql` — создать 12 таблиц.
4. `04_constraints.sql` — добавить интервальные ограничения-исключения.
5. `05_indexes.sql` — создать целевые и поддерживающие индексы.
6. `06_comments.sql` — добавить комментарии к таблицам и полям.

Выполнять скрипты в указанном порядке от имени пользователя, имеющего права на создание схемы и расширения. В данном учебном Docker-проекте используется пользователь `postgres`.

## 7. Контроль после создания

После выполнения DDL необходимо проверить:

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'frac_core'
  AND table_type = 'BASE TABLE'
ORDER BY table_name;

SELECT conrelid::regclass AS table_name, conname, contype
FROM pg_constraint
WHERE connamespace = 'frac_core'::regnamespace
ORDER BY conrelid::regclass::text, conname;

SELECT schemaname, tablename, indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'frac_core'
ORDER BY tablename, indexname;
```

Ожидается 12 таблиц. Результаты фактической проверки будут внесены в README после запуска на локальном PostgreSQL пользователя.
